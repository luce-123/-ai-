# 国内 AI Coding Plan 数据集 + 比价原型

把国内各家 AI 编程订阅套餐整理成**结构化、可校验、可归一化对比**的数据，并据此渲染一个可交互的比价页面。

- 数据文件：[`data/plans.json`](data/plans.json)
- 前端页面：[`index.html`](index.html)
- 校验：`node codingplan/scripts/validate.js`
- 比价报告：`node codingplan/scripts/report.js`（加 `--json` 输出机器可读格式）
- 渲染测试：`node codingplan/scripts/smoke-test.js`
- 采集层测试：`node codingplan/scripts/collect/test.js`
- 渲染器卡死防护测试：`node codingplan/scripts/collect/test-render-guard.js`
- 迁移脚本测试：`node codingplan/scripts/test-migrations.js`
- 口径说明、字段字典、维护规范见下文

当前覆盖：**17 家厂商 / 21 个套餐 / 68 个档位 / 价格区间 ¥0 ~ ¥1400**。

---

## 一、为什么不是简单地抄一份表格

原站（codingplanhub.cn）是一张信息量很大的静态聚合页，但它有个硬伤：**各厂商计费口径完全不同**，用户没法横向比。

| 计费口径 | 单位 | 典型厂商 |
|---|---|---|
| `token` | Token | 腾讯云、华为云、联通云、阿里百炼 |
| `requests` | 请求次数（含 5h/周/月三重限流） | 快手、京东云、讯飞、百度、UCloud |
| `credits` | 积分 / Credits | 小米 MiMo、智谱 GLM |
| `agent_quota` | Agent 额度 / 燃料值 | 字节火山方舟 Agent Plan |
| `subscription` | 席位（不公开额度） | Cursor、摩尔线程、OpenCode Go |

所以数据集额外做了**归一化层**（`derived` 字段），把能算的都算出来，算不出来的明确留空而不是编一个数。

## 二、字段字典

### 顶层结构

```
meta          数据集元信息（快照日期、计数、估算规则、免责声明）
billing_types 计费口径枚举 + 是否可跨厂商比较
use_cases     场景标签枚举（尝鲜 / 学生 / 日常主力 / 重度 / 团队）
vendors       厂商表（17 家）
plans         套餐表（21 个），每个套餐内嵌 tiers 档位数组（共 68 个）
```

### `plans[]` 字段

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | 套餐唯一标识，kebab-case |
| `vendor_id` | string | 关联 `vendors[].id` |
| `name` | string | 套餐官方名称 |
| `billing_type` | enum | 五选一，见上表 |
| `buy_url` | string | 官方购买页 |
| `badges` | string[] | 展示用角标（如 `热门`、`有免费版`） |
| `has_free_tier` | boolean | 是否有 ¥0 档位（由校验脚本强制核对） |
| `min_price_cny` | number | 最低档月价（由校验脚本强制核对） |
| `positioning` | string | 一句话定位，详情页/分享卡片可直接用 |
| `models` | object | `{ count, partial, listed }`，`partial: true` 表示官网只展示了部分模型。**官网未公布时整体缺失**，不许填 0 |
| `tools` | object | 同上，兼容的 IDE / CLI / 插件 |
| `purchase` | object | 可选。**可购买性**：`{ status, as_of, evidence, source, note }`。**缺失 = 未核实，不等于在售**（见下文「数据集缺了一维：能不能买到」） |
| `tiers` | array | 档位数组 |

### `tiers[]` 字段

| 字段 | 说明 |
|---|---|
| `id` | 以 `<plan_id>-` 为前缀，便于反查 |
| `name` / `price_cny` / `price_display` | 档位名与实际价格（number 用于计算，display 用于展示） |
| `price_list_cny` | **官网标价（原价）**。只有官网同时展示原价与优惠价时才存在，此时 `price_cny` 是折后实付价。UI 用划线展示 |
| `price_currency` / `price_foreign` | **外币定价**。官网以美元标价时出现，`price_foreign` 是官网原币金额；此时 `price_cny` 只是汇率估算值，**不是官网数字**，UI 必须显示原币 |
| `price_note` | 优惠条件，如「首月 ¥9.9」「连续包季 8 折（月付原价 ¥118）」「季付 ¥120/季（月均 ¥40）」。外币档位必须写明汇率估算 |
| `billing_period` | `monthly` / `quarterly` |
| `quota` | `{ raw, unit_key, value, window, multiplier, window_limits, derived }` |
| `derived` | 归一化结果，见下 |
| `agent_concurrency` | `{min, max}` Agent 并发数，未公开则无此字段 |
| `context_window` | 上下文窗口，单位 token |
| `multimodal` | 是否支持多模态 |
| `use_case` | 场景标签，取自 `use_cases` 字典 |
| `highlights` | 卖点列表 |
| `price_history` | `[{ date, price_cny }]`，**价格追踪的基础**，每档至少一条 |

### 价格口径：为什么价格要拆成四个字段

2026-09-28 的渲染实测确认，**各厂商官网展示价格的口径根本不统一**，而这一层差异直接决定用户算出来的钱对不对：

| 官网实际展示 | 涉及厂商 | 本库怎么存 |
|---|---|---|
| 季付价格（¥120/季） | 摩尔线程 | `price_cny` = 月均 ¥40，`price_note` 记原值 |
| 折后价 + 原价并列（¥94.4 / ¥118） | 智谱 | `price_cny` = ¥94.4，`price_list_cny` = 118 |
| 美元标价（$20/60/200 per mo） | Cursor、OpenCode | `price_currency`=USD、`price_foreign`=原币额，`price_cny` 仅为汇率估算 |
| 宣传语「¥9.9 起」 | 火山方舟等 | 不进 `price_cny`（那是引流价，不是档位价） |
| 月度标价（¥49） | MiniMax、腾讯云 | `price_cny` = ¥49，无原价字段 —— **官网没有原价，就不该有原价字段**（曾误记成 ¥44.1，见第七节第 6 项） |

约定只有一条：**`price_cny` 永远是「可比的人民币月费」**，其余字段只负责说明「这个数字是怎么来的」。因此：

- 有 `price_list_cny` 时它一定 **大于等于** `price_cny`（校验会拦），UI 用划线展示
- 有 `price_currency` 时 UI **必须显示原币**，人民币只能以 `≈` 出现——否则用户会以为官网标的就是 ¥140
- 外币档位**不参与**人民币归一化成本估算（校验会拦），汇率天天变，算出来的是假精度
- **官网怎么标，就怎么记**。不许用系数把官网数字"换算"成数据集里原有的数字 —— 那等于用假设证明假设（第七节第 6 项是实例）

### `derived` 归一化字段（核心）

| 字段 | 含义 |
|---|---|
| `quota_month` | 额度折算到「每月」（周额度 ×4，5 小时额度 × 窗口数） |
| `cost_per_unit` | `price_cny / quota_month`，单位原始成本。**只能在同 `billing_type` 内比较** |
| `est_tokens_month` | 估算月 Token 量（仅 token / requests 两类可算） |
| `cost_per_1m_tokens_est` | 每百万 Token 成本，**跨口径参考值** |
| `confidence` | `high`（厂商直接给了 Token 数）/ `medium`（有倍率关系）/ `low`（依赖估算假设） |

> 估算假设写在 `meta.estimation_rules` 里，可调整：
> 每次请求 ≈ 8,000 tokens、每日 5 个限流窗口、每月 30 天。
> **`requests` 类套餐的估算值只能用于排序参考**——真实可用量受 5 小时窗口硬约束，不是平均分布。

## 三、当前数据能得出的结论（脚本实测）

**标准 Token 计费最便宜：**腾讯云 Hy 系列，¥0.72 ~ ¥0.80 / 百万 Token，且**档位越高单价越低**；华为云 Max（¥0.908）次之。联通元景虽然 ¥15 起售最低，但单位成本 ¥2.5 / 百万 Token，是腾讯 Hy 的 3 倍多——**起售价低 ≠ 性价比高**，这正是归一化层存在的意义。

**按请求计费最便宜：**京东云，¥0.017 / 千次请求，比第二梯队（讯飞、百度、阿里百炼，约 ¥0.035）便宜一半。UCloud 单价最高（约 ¥0.40 / 千次），但它是唯一给出 5 小时/周/月三重明确窗口数值的厂商，透明度最好。

**免费档只有 2 个：**摩尔线程 Free Trial（每日限量 100 名）、Cursor Hobby。

**生态兼容 TOP：**智谱 GLM Coding Plan（20+ 工具）、阿里云百炼 Token Plan（16 工具）；模型覆盖 TOP：讯飞星辰 Astron（15 模型）、Cursor（14 ）、OpenCode Go（13）。

**但「最便宜」的前提是「买得到」：**已核实的 21 个套餐里有 4 个**不是正常在售** —— 千帆 Coding Plan 全档位停止新购（自 2026-07-13）、阿里百炼 Coding Plan 限量抢购、Kimi 暂停 C 端新订阅（2026-07-19）、快手无法核实。价格排序的前提是能买到，所以前端把「可购买性」排在价格信息之前，详情页也把它排在「档位与定价」前面。详见下文「数据集缺了一维：能不能买到」。

## 四、比价原型（前端）

在 `codingplan/` 目录下起一个静态服务器即可打开（`data/plans.js` 已内联数据，所以直接双击 `index.html` 也能看）：

```bash
cd codingplan
python -m http.server 8899        # 然后访问 http://127.0.0.1:8899/
```

### 页面结构

| 区块 | 作用 |
|---|---|
| 概览统计 | 厂商 / 套餐 / 档位数、最低起售价、单套餐最多模型数 |
| 筛选器 | 关键词（命中厂商、套餐、档位、**模型名、工具名**）、计费口径、适用场景、月费上限、只看有免费档 |
| 排序 | 月费 / 单位成本 / 折算额度 / 模型数 / 工具数 / 厂商名 |
| 矩阵视图 | 一行 = 一个档位（68 行），带对比勾选框 |
| 卡片视图 | 一卡 = 一个套餐，卡内档位 tab 可切换，价格与额度实时联动 |
| 对比器 | 最多同时对比 4 个档位，弹层里逐维度并排，最优值标绿、有差异的单元格高亮 |
| 详情弹层 | 套餐定位、全档位表、模型/工具清单、价格追踪、购买链接 |
| 口径说明 | 五类计费口径的含义、档位数、是否可跨厂商比较，以及折算假设 |

### 移动端 App 原型（`app/`）

桌面版是「一张大表」，`app/` 是**同一份数据在 390px 里的一版重做**：左侧设计说明 + 中间手机框的可点原型。双击 `app/index.html` 即可打开（同样内联 `data/plans.js`，不引 `fetch`）。

| 屏 | 职责 | 入口 |
|---|---|---|
| 首页 | 60 秒建立口径安全感：快照、向导入口、榜单速览、最近变更、口径速查 | tab |
| 比价榜 | 68 档全量浏览 + 搜索 + 筛选 + 排序 | tab |
| 选型向导 | 三问（用量 / 工具 / 预算）出推荐 | tab（居中主按钮） |
| 变更动态 | 只由数据推导的事件流；没有数据就承认判断不了 | tab |
| 说明 | 口径折算表、数据可信度、来源与免责、**还没做的** | tab |
| 我的关注 | 长期清单：4 维排序、价格追踪承诺 | 首页区块 + 顶栏（**不占 tab** —— 390px 下 6 个图标必然挤） |

几条规定：

1. **可购买性只到套餐级**：数据集没有档位级字段，所以凡出现在档位行上的徽章都强制跟一个「· 该套餐」，详情页标题直接写「可购买性 · 套餐级」。
2. **「优先展示在售」是重排不是过滤**：非在售下沉到末尾折叠区，`#rankCount` 仍显示总数、**行数守恒**（`5+63=68`）。让「买不到」能被筛掉，等于鼓励用户假装它们不存在。
3. **价格追踪按当前档位讲**：混着画会把「档位不同」伪装成「价格波动」。
4. **价格变动标记诚实留白**：68 档全部只有 1 个快照，一律标「价格未追踪」—— 是判断不了，不是没有变动。
5. **搜索命中要解释**：搜「Cline」命中的是 `*tools.listed*`，卡面上根本看不到，所以另开一行「命中理由」。

### 几个刻意的设计取舍

1. **单位成本列会显示置信度圆点**（绿=厂商直接公开 Token 数、黄=按倍率折算、灰=依赖估算假设），避免把估算值当成实测值。
2. **「单位成本」排序时会弹出提示条**：说明请求次数类是估算值、积分/Agent 额度/订阅类不参与跨厂商比较因而按价格垫底。这直接对应上文那条「起售价低 ≠ 性价比高」。
3. **无法折算就直说**：29 个档位显示「未公开额度」，而不是编一个数让它看起来能比。
4. **不伪造价格曲线**：目前每个档位只有 1 个历史点位，详情页就老实写「首次记录」，而不是画一条虚假的平线。等采集脚本跑起来，曲线自然会出来。

### 测试

```bash
# 需要 jsdom：cd <node 工作区> && npm install jsdom
NODE_PATH=<node工作区>/node_modules node codingplan/scripts/smoke-test.js   # 桌面版
NODE_PATH=<node工作区>/node_modules node codingplan/scripts/test-app.js     # App 原型
```

App 原型那套的关键分组：**12 静态守卫**（`app.js` 引用的每个 id 必须存在于 HTML —— 这条拦过一次「`renderHome` 引用不存在的 `#homeFavs` → 启动崩溃 → 手机框全空」）、**13 可购买性**（行数守恒证明不是过滤）、**14/14b 文案与实现一致**（「还没做的」清单不得出现过时说法；并另起一个 jsdom 用 `#rank?cmp=…` 打开，验证分享链接真能复现）、**15 搜索**（热词必须能在数据里找到出处、搜索词里的 HTML 不会被渲染成标签）、**16 我的关注**（价格标记一律 `--na`、不出现涨跌箭头）。

布局另有一道真机体检（jsdom 不做排版，量不出溢出）：

```bash
NODE_PATH=<node工作区>/node_modules node codingplan/scripts/probe-layout.js   # 真实 Chrome，390px
```

用 jsdom 真实执行页面脚本，覆盖 **106 项断言**：渲染数量、搜索/筛选/排序结果、对比器全链路（勾选 → 上限保护 → 面板渲染 → 差异高亮 → 移除）、卡片档位切换、详情弹层、主题切换、**价格口径展示**（划线原价的数量必须与数据里记录原价的档位数一致、外币档位必须显示原币且人民币只能以 `≈` 出现）、**可购买性展示**（非在售状态必须带截至日期、未核实必须写出来而不是留白、二手依据不得冒充实测）、运行期零报错，另有静态一致性检查（`app.js` 引用的全部 id 是否存在于 HTML、`[hidden]` 与 `.pricelist` 两条防御性规则是否还在）。

> 踩过一次坑：`smoke-test.js` 用 `String.replace()` 把脚本内联进 HTML 时，**替换参数必须写成函数形式**。字符串形式里 `$'` `$&` `$$` 是特殊模式，而数据与代码里天然有 `"$20"`、`'（官网 $'` 这类内容——会把 HTML 的其余部分当成「匹配之后的文本」注入进来，产生让人一头雾水的 `SyntaxError`。
>
> 另一个坑：卡片视图测试会把视图切走，而**矩阵的 DOM 会停在切换前的状态**。此时改搜索只会重渲染卡片，矩阵行数还是旧的。在这之后再断言矩阵内容，必须先切回表格视图。

## 五、采集层（价格怎么更新）

`scripts/collect/` 是一套**只写报告、不改数据**的采集流水线：

```
抓取(fetch) → 提取(extract) → 比对(diff) → pending-changes.json → 人工确认 → apply 写库
```

```bash
node codingplan/scripts/collect/run.js              # 在线抓取（需渲染的走浏览器，其余走静态 HTTP）
node codingplan/scripts/collect/run.js --offline    # 用 fixtures 跑，不联网也不开浏览器，用于自测
node codingplan/scripts/collect/run.js --no-render  # 关掉浏览器渲染，只做静态抓取
node codingplan/scripts/collect/run.js --probe      # 全部抓一遍，复核「需渲染/失效」的判断是否还成立
node codingplan/scripts/collect/run.js --json       # 只吐 JSON

node codingplan/scripts/collect/probe-render.js     # 单独探测浏览器渲染效果（--keep 留存渲染产物）
node codingplan/scripts/collect/probe-actions.js tencent-general-token-plan
                                                    # 探测「点哪个 tab 才会出价格」（--keep 留存产物）
node codingplan/scripts/collect/probe-actions.js tencent-general-token-plan --click="text=通用 Token Plan"
                                                    # 已经看出该点哪个了，直接定点验证这一个
node codingplan/scripts/collect/probe-actions.js tencent-hy-token-plan --dump
                                                    # 只看基线可见文本，不点任何东西
node codingplan/scripts/collect/probe-jsonld.js     # 扫一遍所有来源，看谁内嵌了结构化报价
                                                    # （--no-render 只扫静态、--only=xxx 限定来源、--keep 留存命中 HTML）
node codingplan/scripts/collect/apply.js --dry-run  # 看会改什么（不写入）
node codingplan/scripts/collect/apply.js            # 应用 decision="apply" 的项
```

### 浏览器渲染后端：让「空壳页面」也能抓

14 个来源需要渲染（静态 HTML 是几百字节的空壳，或价格不在首屏的可见文本里），其中 8 个渲染后能逐档取到价格。这里没有引入 puppeteer/playwright，而是**用 CDP 直连本机已装的 Chrome/Edge**：

- 零新增依赖 —— 用 Node 22 内置的全局 `WebSocket` 说 DevTools 协议，不需要下载那 ~500MB 的 Chromium
- 只启动一次浏览器，每个页面开一个 tab（启动开销约 0.3s）
- 等「价格文本出现」而不是死等固定时长，命中即返回，又快又稳
- 拿不到浏览器时**自动退回静态抓取并在报告里标注**，不会把空壳误判成「页面变了」

实测把自动取到数据的来源从 **6/20 提到 11/20**，一致性确认档位从 5 个提到 **30 个**。

### 页面交互：价格藏在 tab 后面怎么办

渲染解决的是「JS 跑完页面上就有」，但还有一类页面是「**要人点一下才出现**」——腾讯云活动页就是标本：Hy 系列默认渲染，通用系列得先点「通用 Token Plan」这个 tab。

所以渲染器支持了 `render.actions`，并且**刻意排在 `waitFor` 之前执行**，于是「先切到目标 tab，再等价格出现」是天然支持的：

```json
"render": {
  "actions": [{ "click": "text=通用 Token Plan", "wait": 1500 }],
  "waitFor": "集成主流国产模型",
  "waitForMax": 20000
}
```

`click` 支持两种定位：`text=完全匹配的可见文本`（tab 通常没有稳定 id，只能靠文本）和普通 CSS 选择器。用 DOM 的 `.click()` 而不是合成鼠标事件——前端框架的 tab 基本都监听 `click`，合成 `PointerEvent` 在部分框架上反而触发不了。文本匹配要求元素宽高 > 2px，否则会点到隐藏的同名节点。

**`waitFor` 用什么是关键。** 这里不能写档位名：通用系列的档位叫「个人版–体验套餐（Lite）」，而 Hy 那行是「Hy 个人版–体验套餐（Lite）」，前者是后者的子串，`waitFor` 是正则包含匹配，**会假命中**——点没点上都"命中"，错误就被掩盖了。改用「集成主流国产模型」（只在通用系列卡片里出现）才真正证明了 tab 切过去了。

`probe-actions.js` 是配套的探测工具，三档用法：默认自动试（列出页面上所有像 tab 的可点元素，逐个在全新渲染里点一遍，报告哪些会让新金额出现）；`--click=` 定点验证某个元素；`--dump` 只看不点。

> 这个能力立刻回收了成本：腾讯云两个来源此前被判为 `headline-only`（页面只有「39元/月起」），实际上四档价格**全都在渲染后的文本里**，只是早期静态抓取看不到。加上交互后，Hy 4 档（28/78/238/468）+ 通用 4 档（39/99/299/599）全部与数据集逐字吻合。真实的渲染日志：
>
> ```
> ["点击「通用 Token Plan」","命中等待条件","首次未命中等待条件，重试后成功"]
> ```

### 实测结论：21 个来源的状态分布

| status | 数量 | 含义 | 代表 |
|---|---|---|---|
| `verified` | 11 | 能稳定提取到各档位价格，可自动比对 | 华为云、智谱、MiniMax、Kimi、摩尔线程、联通元景、阿里百炼、**腾讯云 Hy / 通用**、**千帆 ×2**（Coding Plan + Token Plan） |

| `noisy` | 2 | 有价格文本但混着优惠券/其他产品 | 京东云、阿里百炼 Coding Plan |
| `usd-pricing` | 2 | 官网美元标价，数据集里的 ¥ 是汇率换算值 | Cursor、OpenCode |
| `broken` | 1 | 链接已失效 | **[快手 KwaiKAT（404）](https://www.streamlake.com/marketing/coding-plan)** |

> 讯飞与 UCloud 原先判为 `spa`，渲染实测发现渲染出来的是登录页（「微信扫码登录」「获取验证码」），因此改判 `login` —— 这类判断必须实测，不能靠猜。

> 腾讯云两版原先判为 `headline-only`（「只有 39元/月起」），实测**推翻了这个结论**：Hy 系列四档价格就在渲染后的可见文本里，通用系列点一下 tab 也有。原判错的根因是**早期只找「数字+元」形态**，而页面写的是「日常价：\n28\n.00\n元/月」（数字与单位被拆到不同行）。教训是：判 `headline-only` 之前得先确认自己的提取口径没漏。

> **千帆原先也判为 `headline-only`**，因此从 3 个降到 2 个。而真正的问题不是提取口径，是**来源 URL 指错了产品** —— 详见下文「来源 URL 可能指向了另一个产品」。

> **数据集里快手的 `buy_url` 实测已 404**，需要重新找官方定价页。数据本身暂未改动，因为不能凭空猜一个新地址。

### 五种提取策略，各管一类页面

| 策略 | 适用 | 能检测涨降价 | 例子 |
|---|---|---|---|
| `pair` | 页面把「标题+描述」成对塞在内联 JSON 里，一次拿到价格+额度 | ✅ | 联通元景 |
| `blocks` | **按「独占一行的档位名」分块**，块内取价与额度。默认吃渲染后的可见文本；配 `on:'html'` 则改吃静态 HTML 去标签后的文本 | ✅ | 华为云（旧）、智谱、Kimi、MiniMax、摩尔线程、腾讯云两版；**千帆**（`on:'html'`） |
| `jsonld` | 页面内嵌的 **schema.org 结构化报价**（`@type: Offer` 的 name/price/priceCurrency） | ✅ | Cursor |
| `cards` | 页面把每档序列化成一张**卡片对象**（档位名/价格/单位/额度都在同一对象里） | ✅ | 华为云、百度千帆 Token Plan（同一页两种计费口径，靠 `filter` 二选一） |
| `regex` | 只有一串价格，分不清归属 | ❌ 只做一致性确认 | 阿里百炼 |

四个关键细节：

- **`blocks` 要求档位名独占一行**，不是因为好看。智谱正文里有「6倍 Lite 用量额度」这样的句子，只按关键词分块的话这个「Lite」会被误当成下一个档位的起点，把上一块截断。用行边界约束后精确区分。
- **行边界还顺带解决了「同一页面上多个套餐系列」**。腾讯云的 Hy 系列档位名是「Hy 个人版–体验套餐（Lite）」，通用系列是「个人版–体验套餐（Lite）」——通用版的 `blockRe` 用 `(?:^|\n)[ \t]*个人版–` 约束，Hy 那行前面站着一个「Hy 」，不是行首，所以**不会**被误取。这条有断言守着：点过 tab 之后页面同时含两个系列，通用版仍只取到 4 档且 0 个无法归属的候选值。
- **`blocks` 的 `on:'html'` 是给官方文档站用的**。文档站把套餐表格直接写在静态 HTML 里（千帆 Coding Plan 的文档页 386KB，¥40/¥200 与三档请求限额都在正文表格中），去标签后的文本同样有稳定的块边界，却省掉一次浏览器渲染 —— 千帆那条来源因此从「要渲染」变成「**静态 0.5 秒**」。实现上的关键是块级标签的闭合要换成 `\n`，尤其是表格：`<td>Lite</td><td>¥ 40 / 月</td>` 必须变成两行，否则档位名不再"独占一行"。
- **`regex` 只确认不猜测**。第一版实现里，腾讯云页面的「39元/月起」被匹配到 3 次，按序号对齐得出「Standard 99→39、Pro 299→39」两条假变更——**拿不准就不猜**，比"看起来抓到了"重要。（该来源后来升级成了 `blocks`，能逐档比对了。）


### `cards`：页面把每档序列化成一张卡片对象

前端的定价区通常是「循环渲染一个数组」，于是**每档套餐在页内 JSON 里就是一张卡片对象**，档位名、价格、单位、额度全在同一对象内。这是形态最好的一类来源 —— 它天生带档位名，所以能按档位对齐、能发现涨价，而且不吃 tab 交互。两个实测形态：

```
华为云（藏在 <textarea class="activity-visible-data"> 里，JS 读它来渲染）
  {"header":{"titlePc":"Lite"}, "description":{"specs":[{"name":"每订阅月","spec":"5000 万 Tokens"}]},
   "price":{"currency":"¥","origin":59,"current":59,"unit":"/月"}}

百度千帆 Token Plan
  {"title":"Mini","price":"4.9","unit":"/月","deletePrice":"9.9","hotTags":[{"text":"1000 万 Tokens /月"}], …}
```

**为什么不按 JSON 路径取值**：字段散在不同层级（`header.titlePc` 与 `price.current`），但都在同一张卡片对象内、且这些键名在本站内不重复，所以在卡片文本上按键名取第一个匹配就够用，还少一层配置。真正需要配的只有三件事：

- `cardKeys` —— 怎么圈定"一张卡片"（必须同时出现的键名），用来把卡片和页面上其它带价格的杂项对象分开
- `filter` —— 同一档位有多张卡片时认哪一张。**这是真实存在的形态**：千帆 Token Plan 每档都有「积分制」和「Token 制」两张卡（同为 Mini/Lite/Pro/Max），只认 `Tokens` 那张
- `quotaRe` —— 额度写法太不规整，用一个带捕获组的正则比配键名可靠

三个踩过的坑，都在断言里守着：

- **`maxLen` 必须按实际卡片大小给**。华为云的卡片对象有 2.4KB，用默认的 1500 会把整张卡片直接丢掉 —— 这正是它最初被误判成"没有结构化报价"的直接原因。**"扫不到"和"扫了但被过滤掉"必须能区分**，否则会一路错到底还找不到原因。
- **同一档位出现两张不同报价的卡片时要报警，不能默默取第一张**。静默取第一个会把「页面结构调整了」伪装成「价格没变」，这是最坏的失败方式。实现上按档位名归组，价格+单位不一致就写一条警告（含两个具体数值），让人来裁决。
- **`origin` 常等于 `current`**（同一个数被填了两遍，不是在打折）。只有两者**确实不同**时才记 `listPrice`，否则前端会凭空多出一条划线价。

还有一条不属于 `cards`、但正是用它才暴露出来的坑：

> **货币符号必须归一化，否则会静默漏判。** 卡片里的货币写作 `"currency":"¥"`，而比对器判断"是不是外币"用的是 `currency !== 'CNY'` —— 于是 `"¥"` 被当成外币，四档人民币报价**整条跳过**、进了「外币定价」记录，报告上安安静静，看起来像"这来源本来就没法比对"。实测就是这么发现的：改用 `cards` 策略后，华为云从「4 档确认」变成了 4 条外币记录。现在 `¥/￥/CNY/RMB/元/人民币 → CNY`、`$/USD → USD` 统一归一，并且有一条断言专门守着「华为云 4 档确认 + currencyNotes 必须为空」。

### `jsonld`：一条绕开交互的路子


不少 SaaS 定价页为了 SEO 会把价格写进 `<script type="application/ld+json">` 的 `offers` 里，字段规整（`name` / `price` / `priceCurrency`），比从渲染文本里猜可靠得多。更关键的是它**不受 tab 交互影响**：

> Cursor 页面上 Pro+ / Ultra 是切换 tab，**点了也不换价**（点击能命中元素，但卡片上的 $20 纹丝不动）——靠可见文本根本拿不到这两档的价格。而结构化数据里全量报价一直都在：`Hobby $0 / Pro $20 / Pro+ $60 / Ultra $200 / Teams $40`。而且静态 HTML 里就有（348KB），**连浏览器都不用开**。这条来源因此从「不做自动提取」变成了可自动比对。

两个实现上的坑：

- **同一份数据会出现多次、且形态不同**：Next.js 之类的框架会把 JSON 再塞进 RSC 载荷，于是同一对象既有干净的 `"name":"Pro"`，又有三层转义的 `\\\"name\\\":\\\"Pro\\\"`。做法是**先把 haystack 压平**（`replace(/\\+"/g, '"')`）再匹配，靠去重收尾，不必分别处理两种形态。测试夹具同时保留两种形态以覆盖这一步。
- **必须能发现新增档位**。`ignore` 列表只用来排除「明确知道、但不属于本套餐」的档位（Cursor 的 Teams 是另一条产品线，本站未建模）。**不认识的档位名一律不许静默丢弃**——测试里专门有一条：不配 `ignore` 时 Teams 必须浮出来。
- **对象是嵌套的，正则数不了花括号**。这是最隐蔽的一个：真实形态是 `"offers":[{Offer},{Offer}]`。用「不含嵌套花括号」的正则（`/\{[^{}]{0,900}\}/g`）会漏掉所有内层 Offer，报成"这个来源没有结构化报价"；换成配平扫描但「找到最外层就跳到结尾」的版本，又只剩外层那个容器 —— 拿产品名 + 第一个子报价的价格冒充一条报价（Cursor 就这样报出过 `Cursor / USD 0`，报价数从 5 掉到 1）。现在这套扫描逻辑收在 `lib/jsonwalk.js`，探针与生产提取器共用，两个方向都有断言锁住。

### 把 `jsonld` 当常规武器扫一遍：21 个来源的实测清单

Cursor 的收获（结构化数据比可见文本可靠得多）值得当成一条通用路线去验证，所以写了 `probe-jsonld.js` 逐源扫描有无内嵌报价。**结论是这条路并不通用 —— 值得记下来，省掉以后重新试一遍的功夫：**

> 这次扫描跑于在册 20 个来源时。此后新增的 `baidu-qianfan-coding-plan`（官方文档页）按同一口径单独核对：45,585 B 的夹具里 `application/ld+json` / `@type` / `price` / `offers` **零命中**，与下表结论一致 —— 所以是 21 个来源全部确认，不是「20 个扫过、1 个没看」。

| 来源 | 结构化报价 | 说明 |
|---|---|---|
| Cursor | ✅ **可直接用** | 5 条 `@type:Offer`，4 条对上档位（Hobby/Pro/Pro+/Ultra），已接 `jsonld` 策略 |
| 百度千帆（产品页） | ⚠️ 有，但形态不同 | 8 条对象名是表头标签（`限时权益`/`模型支持`）而不是档位名。真正的逐档数据在卡片数组里 → **已接 `cards` 策略**。**注意：这一页现归属 `baidu-qianfan-token-plan`**，它属于另一个产品，见下节 |
| 华为云 | ⚠️ 有，但对象没名字 | 价格在 `"price":{"currency":"¥","origin":59,"current":59,"unit":"/月"}`，档位名在**同级的** `header.titlePc` —— 起初误判成"卡片不带档位名" → **已接 `cards` 策略** |
| 快手 | ❌ 噪声 | 404 页里混着一块无关的 `Offer` |
| 其余 17 个 | ❌ 确定没有 | 页面里**连一个价格类字段名都不出现**，所以这个"没有"是可靠的 |

这里有个设计取舍值得说：探针把"0 条报价"拆成两桶 —— 「连价格字段都没有」（17 个，结论可靠）和「有价格字段但没扫成档位报价」（值得人工看一眼）。**这个拆分直接救了这一轮**：华为云和百度千帆都落在第二桶里，而它们恰恰是真正有数据的那两个。如果只报一个 0，这两个来源就会被误判成"没有结构化数据"抛掉。

两个副产品发现：

- **`PRICE_KEYS` 的口径漏了会让探针产生假阴性**。华为云的键名是 `current`/`origin` 这种通用词，最初不在表里，整个来源被误报成"没有结构化报价"。补进去之后加了佐证条件：这类通用键名**必须和 `currency` 或 `unit` 同时出现**才认，否则页面上随便一个"当前值"字段都会被当成报价。
- **"卡片对象不带档位名"这个判断是错的**。当时只看了 `price` 那一层就下了结论，实际档位名在**同级的** `header.titlePc`。教训很具体：**"我没在当前这层找到"不等于"它不在这个对象里"** —— 下结论前把整张卡片打印出来看一眼。后来 `cards` 策略干脆不按路径取值，只看整张卡片的文本。

### 来源 URL 可能指向了**另一个产品**：一次产品线混淆

千帆这条来源原本被判为 `headline-only`（"只有宣传语"），附注写着「只有 4.9 元即可畅享 Token Plan 全场，与本站 ¥40 起不属于同一档位，属于另一个引流产品」。这个判断方向是对的，但结论下轻了 —— 2026-09-28 把页面原文读完之后，发现它**不是引流产品，而是接替 Coding Plan 的另一条产品线**：

| 证据 | 内容 |
|---|---|
| 页内 `<title>` | 「百度千帆 **Token Plan 个人版**-百度智能云」 |
| 页内卡片 | 4 档 Mini/Lite/Pro/Max，且每档有**积分制与 Token 制两张卡** |
| 页面自述 | 「**完全取消 Coding Plan 原有的三层限流体系**」—— 这句话把"Coding Plan"当**前辈**来引用 |
| 官方文档页 | Coding Plan 的文档仍写着 ¥40/¥200 + 18,000/90,000 次请求，与数据集**逐字一致** |
| **官方公告**（同日补核） | 「自 2026 年 7 月 13 日起，Coding Plan 产品将停止接受新购订单，Token Plan 个人版全面开放购买」 |

**所以数据没错，错的是来源 URL —— 它指向了另一个产品的销售页。** 这条更正很有代表性：如果当时图省事，把页面上读到的价格（`deletePrice` 恰好也是 9.9/40/200/600）直接接给 `baidu-qianfan-coding-plan`，两边价格梯子**碰巧同为 40/200**，比对结果会是漂亮的「2 档确认、0 变更」—— 一个看起来完全正确、实际什么都没验证的假确认。**价格巧合比价格不符危险得多**，因为它不报错。

> **补记（同日、查到一手公告后修正）**：上一版把两者的关系写成「两条并行在售的独立产品线」，**这个说法不准确**。官方公告 [Token Plan 个人版上线及 Coding Plan 停售公告](https://cloud.baidu.com/doc/qianfan/s/Fmrexuejc)（更新于 2026-07-10）写得很清楚：**Coding Plan 全档位自 2026 年 7 月 13 日起停止接受新购订单**，Token Plan 个人版同日全面开放购买；存量 Coding Plan 用户可正常使用至服务周期结束，也可通过一键迁移通道升级。
>
> 也就是说 —— **文档页上的 ¥40/¥200 至今仍然「对」，但它现在描述的是存量用户的价格，不是你能买到的价格。** 这是一个比涨价更难发现的问题：**价格没变，可购买性变了。** 顺带说明本库的一条边界：我们建模的是「官网标价」，而不是「你能买到」—— 见下文「数据集缺了一维：能不能买到」。

现在的处理：千帆改指官方文档页（静态、可解析、逐字吻合）；Token Plan 作为**独立套餐**建条目，不与 Coding Plan 互相比对。这条规矩也写进了 `sources.json` 的 `note` 里。


### 数据集缺了一维：**能不能买到**

顺着快手的死链与千帆的公告往下查，发现 2026 年 7 月前后有一轮集中的**可购买性**变动 —— 而价格往往**没变**：

| 厂商 | 核实到的事实 | 来源性质 |
|---|---|---|
| 百度千帆 | Coding Plan 全档位自 **2026-07-13** 10:00 起停止购买；Token Plan 个人版同日全面开放购买，存量可正常使用至服务周期结束 | 一手官方公告 |
| 阿里云百炼 | Coding Plan Lite **2026-03-20** 停止新购、**2026-04-13** 停止续费升级；Pro 限量抢购、售罄不补；与 Token Plan 无法互相迁移 | 一手帮助中心 |
| Kimi | **2026-07-19** 起暂停 C 端新用户订阅，算力优先保障存量用户；公告称将逐步放开 | 媒体转引官方原文 |

| 快手 KwaiKAT | 官方营销页 404、官方产品页自己仍在推广该死链、无任何公开定价页 | 自核，**无法核实** |

**为什么必须单独立一维**：涨价会被采集器抓到并报警，**停售不会** —— 报告上依然是漂亮的「2 档确认、0 变更」。千帆就是活例子：它的 ¥40/¥200 至今逐字准确，但那一页现在描述的是**存量用户的价格**，不是新用户能买到的价格。**价格对了，可购买性变了。**

字段是可选对象 `purchase`，缺失即表示未核实：

```json
"purchase": {
  "status": "closed_new",
  "as_of": "2026-07-13",
  "evidence": "primary",
  "source": "https://cloud.baidu.com/doc/qianfan/s/Fmrexuejc",
  "note": "官方公告：Coding Plan 全档位自 2026-07-13 10:00 起停止接受新购订单……"
}
```

`status` 五态：`on_sale` 在售 / `limited` 限量抢购 / `closed_new` 停止新购（仅存量可用） / `login_only` 需登录购买 / `unverifiable` 查过但查不到。

三条硬规矩，`validate.js` 与断言里都锁着：

- **`as_of` 不可省。** 没有日期，前端就会把「2026-07 停售」当成「今天停售」。所有非 `on_sale` 状态在界面上**一律带「（截至 YYYY-MM-DD）」**。
- **`evidence` 区分一手 / 二手。** Kimi 那条只有媒体转引，界面就标「依据：媒体转引官方原文」，不冒充厂商实测。
- **`unverifiable` 与「缺失」是两件事。** 「查了但查不到」（快手）和「还没查」（其余 16 个）必须能区分开 —— 这其实是本库早就记下的那条教训（"扫不到"和"扫了但被过滤掉"必须能区分），在这里再兑现一次。

**界面上「未核实」必须写出来，不能留白。** 留白会被读成「没限制、可以买」。所以卡片里加了一行「可购买性」，详情页有独立区块（并排在「档位与定价」之前 —— 买不到的话，价格无从谈起），缺失态显示「未核实」且注明**未核实不等于在售**。这和 `models`/`tools` 留空时是同一套做法：「官网没公开就留空」这条规矩，**只有配上读取端的守卫才算真正落地**。

> 本轮只核实了 5 个套餐，其余 16 个**保持缺失** —— 不猜。剩下的要逐个查，而不是拿一个乐观默认值把整张表填满。


### 渲染器必须自带超时：一次 18 分钟的静默挂死

`probe-jsonld.js` 第一次全量运行时**跑了 18 分钟、一个字都没输出**。进程活着（node 和 chrome 都在），但不推进 —— 没有报错、没有退出，因为 `await` 悬在一个永远不会回来的承诺上。

根因是渲染器里有**没有超时的 await**。CDP 是请求/响应式的，如果标签页那边不再回应（页面里跑了死循环、渲染进程被 OOM kill、Chrome 被系统挂起），响应永远不来。而抓的是别人家的页面，"对方页面有问题"是常态而不是异常。四处都中招：`Page.enable` / `Page.navigate` 这类握手、`Runtime.evaluate`（页面主线程被占住时最典型）、访问 Chrome 调试口的 `fetch`（**Node 的 `fetch` 默认不超时**）、以及 `waitFor` 轮询循环（它的边界管的是"最多等多久"，管不了"单次指令不回"）。

修法是三层，缺一不可：

1. **单条指令超时 + 断线联级拒绝**。`send(method, params, timeoutMs)` 超时就 reject；WS 的 `error`/`close` 要主动把**所有**在飞的 promise 一起拒掉，否则它们只能各自等自己的超时。连 `once()` 这类事件监听者也要唤醒（传 `null`）。
2. **整次渲染的硬上限**（`Promise.race`）。各步超时是串起来的，串起来就会累加，而且只要有一处漏加就又变成永久挂起。外层兜一个总数，到点直接判失败返回。
3. **硬超时触发时顺手掐掉 WebSocket**。`Promise.race` 只是让调用方不再等，被抛在后面的渲染并不会自己停；连接一断，在飞的指令立刻被拒，那条后台流程就顺着自己的 `catch` 收尾，不会变成泄漏。

配套还发现三个同类的"进程干完活却不退"问题，都是句柄泄漏：

- **渲染单例缓存了实例而不是 Promise**。`if (!renderer) renderer = await createRenderer()` 在并发下会让每个调用都看到 `null` —— 实测并发 4 次**起了 4 个 Chrome**，只有最后一个被 `close()`，其余的把事件循环钉住。改成缓存 Promise。（`run.js` 早就写对了，是这个探针没照做。）
- **`Cdp.once()` 的事件先到时没有撤掉兜底定时器**，于是事件循环要多活满一个 `timeout`。
- **CDP 连接没建立成功时，那个 WebSocket 永远不会被关闭**（此时 `cdp` 还是 `null`，`finally` 里的 `cdp.close()` 兜不住）。

修完之后同一次全量扫描：**18 分钟 + 被外部 SIGTERM → 33 秒、正常 exit 0**。诊断手段值得一提：`process.getActiveResourcesInfo()` 直接把答案说出来了 —— `["ProcessWrap","ProcessWrap","Timeout"]`，两个子进程还活着，那就是两个 Chrome。

相应的回归测试是 `test-render-guard.js`：本地起一个返回 `<script>while(true){}</script>` 的页面，渲染进程的主线程被死循环占住、再也不响应任何 CDP 指令，用它能稳定复现"整批任务卡死"。6 条断言覆盖：正常页面能渲染（先证明后端可用，别把环境问题当成修好了）、卡死页面在硬上限内失败、失败原因说明是超时、**卡死之后同一实例仍能渲染别的页面**（一个坏页面不该毒死整轮采集）、`close()` 有耗时上限（它在打印结果之前调用，卡在这里等于结果全丢）。

> 顺手一条运维经验：**别用 `| tail -N` 包住长时间运行的采集脚本**。`tail` 要等进程结束才吐字，卡住时你连"卡在第几个来源"都看不到 —— 这次的 18 分钟有一半是被它掩盖的。改成逐个来源打印进度，并加"连续 3 次渲染超时就熔断、剩余来源退回静态扫描"的兜底。

### 价格口径：同一档位，官网和数据集可能不同

这是实测中最有价值的发现，也是这类工具最容易翻车的地方。官网展示的口径并不统一：

| 来源 | 官网展示 | 数据集记录 | 处理 |
|---|---|---|---|
| 摩尔线程 | ¥120 / **季度** | ¥40 / 月 | `priceDivisor: 3`（单位换算） |
| 智谱 | ¥94.4（季付 8 折）与 ¥118（原价）并列 | ¥94.4 / 月 | 取块内第一个价格，原价另存 `price_list_cny` |
| Cursor | **$20 / $60 / $200 per mo.**（Pro / Pro+ / Ultra） | ¥140 / ¥420 / ¥1400 | 汇率换算，**不做自动比对**；官方价取自页面内嵌结构化数据 |
| MiniMax | ¥49 / 月 | ¥49 / 月 | 无换算（**曾经配过 0.9，已撤销**，见下） |

**这里要立一条规矩，区分两种"换算"：**

- ✅ **单位换算**：页面上写明了单位（「¥120/**季**」→ 月均 ÷3）。数字和单位都在页面上，换算是确定性的。
- ❌ **折扣推断**：页面上**没有**那个数字，系数是从数据集反推出来的。

第二轮复核时发现 MiniMax 的 `priceScale: 0.9` 属于第二类。当初的理由是"数据集记的是连续包月 9 折价，页面记的是月标价，两者对得上"——听起来合理，但点开「连续包月」tab 实测，页面在两个 tab 下给出的月度价**都是 ¥49 / ¥119 / ¥469，全页没有一处 9 折**。那个 0.9 是为了让比对结果显示"一致"而从数据集反推的系数：**那是拟合，不是采集**。

危害不只是"数字错了"：它把一个 11% 的价格差异**永久掩盖**在"0 变更"里。撤掉系数后，采集器第一次如实报出了差异（`¥44.1 -> ¥49`，3 项），然后才走人工核对、改库、回归的流程。**能报出差异的采集器才是有用的采集器。**

所以配置里现在只允许 `priceDivisor`；`priceScale` 在 `sources.json` 的字段说明里被明确标注为「⚠ 不要用来做折扣推断」，并有断言守着（`采集配置里不再有用于折扣推断的 priceScale`）。外币定价一律不参与比对——汇率每天都动，拿它比对只会制造假变更。

### 安全闸门

1. `run.js` **只写报告**，从不碰 `plans.json`
2. 变动幅度 > 50% 一律降级为 `needs_review`，不进自动应用队列
3. `apply.js` 只处理 `decision === "apply"` 的项，默认全部是 `pending`
4. 应用前校验报告里的 `from` 与当前值是否一致，**报告过期就拒绝**（防止用旧报告改库）
5. 应用前自动备份到 `data/backups/plans-<时间戳>.json`
6. 写入后自动重跑 `validate.js`，**校验不过就自动回滚**
7. `price_history` 只追加、不覆盖；同一天重复运行会更新当日点位而不是打两个点

- 口径：MiniMax 无任何系数换算、配置里不存在用于折扣推断的 `priceScale`、**误用 `priceScale` 会触发护栏告警**、`run.js` 确实把 `render.actions` 透传给了渲染器
- 对齐：`tierKeyMap` 按档位名对齐（**打乱顺序后仍 4 档全对**）、未映射的新档位名会被提示而非当成变更、外币不产生变更（Cursor 4 档只记录）
- 一致性：来源覆盖 68 档无遗漏、无悬空 id、报告汇总数字自洽
- 安全：apply 的四道闸门（无 apply 决策时拒绝、dry-run 不写入、过期报告拒绝、结束后还原）

`test-render-guard.js` 另跑 **6 项断言**，用「主线程被死循环占住的本地页面」复现"整批任务卡死"并验证超时兜底真的生效（见上文「渲染器必须自带超时」）。单独成文件是因为它必须开真浏览器，不适合塞进离线测试。

测试开头会自己先跑一遍 `run.js --offline` 刷新报告文件。以前这里假定"你之前跑过采集"，一旦报告是旧的或被别的 `--only` 覆盖过，整个测试会以 `TypeError: Cannot read properties of undefined (reading 'url')` 崩掉——看起来像代码坏了，其实只是前置文件过期。**测试必须自给自足。**

其中「注入一条 apply 决策跑 dry-run」这组会临时改写报告文件，**结束时自动还原**，并验证 `plans.json` 未被触碰。

## 六、数据更新与维护规范

### 更新流程

```bash
# 1. 修改 data/plans.json
# 2. 校验（会核对计数、最低价、免费档、归一化字段自洽性）
node codingplan/scripts/validate.js

# 3. 看结论是否合理
node codingplan/scripts/report.js
```

校验脚本会强制检查以下几类问题，避免手工数据出错：

- `meta.counts` 与实际条数不符
- `min_price_cny` / `has_free_tier` 与档位数据矛盾
- `price_history` 末条价格 ≠ 当前价（改价时忘了记历史）
- `cost_per_unit` 与 `price_cny / quota_month` 不自洽（手算错了）
- 重复的 plan / tier id、非法枚举值、无效的 `vendor_id`

### 加价改价的正确做法

**不要直接改 `price_cny` 就完事**，要同时追加历史快照：

```json
"price_history": [
  { "date": "2026-09-28", "price_cny": 9.9 },
  { "date": "2026-10-15", "price_cny": 19.9 }
]
```

再同步更新 `price_cny` 和 `min_price_cny`，然后跑校验。这样价格曲线和降价提醒才有数据可依。

### 批量修正：写成迁移脚本，不要手改 JSON

一旦发现的是**成批的口径问题**（而不是某一档改价），就该写成迁移脚本：

```bash
node codingplan/scripts/migrate-price-model.js --dry-run       # 1.1.0：Kimi 改名、智谱原价、外币标注
node codingplan/scripts/migrate-price-caliber-v2.js --dry-run  # 1.1.1：MiniMax 撤回反推的 9 折
node codingplan/scripts/migrate-price-caliber-v3.js --dry-run  # 1.1.2：Cursor 补官方美元价
```

好处是每条改动都带出处（渲染实测到的官网原值）、可 `--dry-run` 预览、可重复执行，而且会记进 `meta.changelog`。

**但"可重复执行"比看上去难，实测撞到两次：**

1. **靠旧 id 定位的操作跑第二遍就会炸**。第一轮脚本按 `kimi-code-plan-andante` 找档位来改名——跑过一次后旧 id 就不存在了，重跑直接抛异常。修法是按「旧 id 在就改；旧 id 不在但新 id 在，说明已迁移过，跳过；两个都没有才是真出问题」处理。
2. **旧轮次会把新轮次的修正倒回去**。第一轮脚本写的是"当年应该是什么样"；在第二、三轮之后再跑，它会把后两轮改进过的文案**倒回旧版本**，而 changelog 里新版本号还在 —— 数据和 changelog 自相矛盾。修法是加**轮次守卫**：某个字段若已被更晚的轮次接管，本轮直接跳过。

这两个问题都不会在"只跑一次"的路径上暴露，所以专门有测试守着：

```bash
node codingplan/scripts/test-migrations.js
```

它会验证：三份脚本都能跑通、各自重跑两次数据零变化、**单独重跑第一轮不会覆盖后续轮次的字段**、**倒序+正序乱序执行后仍收敛到同一状态**、迁移后 `validate.js` 依然通过。测试前后自动备份/还原 `plans.json`，绝不留下痕迹。

### 新增厂商 / 套餐

1. 在 `vendors` 里加厂商（`id` 用 kebab-case，配一个主题色，17 家的颜色均已错开）
2. 在 `plans` 里加套餐，`tiers` 里逐档填写
3. 更新 `meta.counts`（跑一次校验就知道该填多少）
4. 想不出 `positioning` 就先留空，别写废话

**成批或来源明确的套餐，请写成脚本**（照 `migrate-add-qianfan-token-plan.js`）：

```bash
node codingplan/scripts/migrate-add-qianfan-token-plan.js --dry-run   # 预览
node codingplan/scripts/migrate-add-qianfan-token-plan.js             # 写入 + 备份 + 自动校验，不过则回滚
```

比起手改 JSON，脚本多出四件东西：每条数据的**出处**（写进 changelog）、`derived` 由价格与额度**现算**（杜绝手写算术错误）、改动前自动备份、写完立刻跑 `validate.js` 且**校验不过就回滚**。而且它是幂等的 —— 已存在就直接跳过，重跑安全。

#### 官网没公布的字段：「留空」不是「填 0」，而且前端必须扛得住

千帆 Token Plan 是第一个**没有 `models` / `tools`** 的套餐：官网只写「支持 GLM、DeepSeek、Kimi 等主流顶尖模型」「适配 Cursor、Windsurf、Cline 等主流 AI Coding 工具」，既没有清单也没有总数。按本库规矩「官网没公开的就留空，不推算填充」，这两个字段整体不写。

代价是前端原本直接读 `plan.models.count` —— 字段一缺就抛 `TypeError`，把整个详情页打白。所以留空时必须同步改读取端，规则是：

- **取值**：`ecoCount(plan, kind)` 返回数字或 `null`（`null` 表示"官网未公布"，**不是 0**）
- **排序**：`null` 一律垫底。当成 0 会让它显示成"生态最差"，而真相是"官网没说" —— 这是两个完全不同的结论
- **渲染**：卡片与详情页都写「官网未公布」，详情页补一句「本库不推算填充」；报表里则注明"另有 N 个套餐未公布，未参与排名"

**同一条规则必须在所有读取点都生效。** 本轮先把 `js/app.js` 改好了，却漏了 `scripts/report.js`，于是报表脚本静默崩在「模型覆盖 TOP5」—— 而且因为没人天天手工跑它，这个崩溃一直没被发现。所以自测里加了一条：**同级脚本都必须 exit 0**。

### 数据可信度原则

- **官网没公开的，就留空**，不要推算填充。全库共 39/68 档有可归一化数据，剩下 29 档明确标注了「未公开」，这是诚实而非缺陷。
  （千帆 Token Plan 更进一步：官网连**模型/工具总数**都没公布，于是 `models` / `tools` 两个字段整体留空，前端显示「官网未公布」而不是 0 —— 详见第六节「新增厂商 / 套餐」）
- **有优惠就看优惠**：`price_note` 与 `promo` 必须如实记录「首月 ¥9.9」这类条件，否则用户按标价算完发现不是这个价，信任就没了。
- **`partial: true` 要保留**：原站展示的模型/工具列表都是截断的（如「+9」），标注 `partial` 是为了避免把"展示了 12 个"误当成"只支持 12 个"。
